# Contracts

## Overview

The Contracts resource manages tenant agreements in the Enspace CRM. A contract belongs to a **Customer** and a **Service**, and may optionally be tied to a specific **Unit**.

Each contract records the benefits included: free monthly meeting room hours, rented lockers, parking spaces, and other benefits — plus the **lease details**: branch location, monthly rental rate, security deposit, lease start/end dates, and payment mode.

Contracts have a lifecycle status (`active` → `renewed` / `expired` / `terminated`) and **cannot be deleted** — attempting to delete a contract throws a `LogicException`. To end a contract, update its status to `terminated` or `expired`.

The response for every contract includes a derived, read-only **`lease_term`** field (e.g. `"July 12, 2025 to July 18, 2026"`), computed automatically from `date_start` and `date_end` — it is not a real column.

The `POST /api/contracts/used-hours` endpoint calculates how many meeting room hours a contract has consumed in a given month, pulling data from the **Bookings** resource.

This resource is **fully public** — no authentication is required.

See [Architecture](/enspace-crm/architecture) for project conventions.

## Endpoints

| Method | URI | Auth Required | Description |
|--------|-----|:---:|-------------|
| `GET` | `/api/contracts` | No | List all contracts |
| `POST` | `/api/contracts` | No | Create a new contract |
| `GET` | `/api/contracts/{id}` | No | Retrieve a single contract |
| `PUT/PATCH` | `/api/contracts/{id}` | No | Update a contract |
| `POST` | `/api/contracts/used-hours` | No | Calculate used meeting room hours for a contract |

:::note
`DELETE /api/contracts/{id}` is **not implemented** — the controller has no `destroy()` method. The model's `boot()` method also throws a `LogicException` on any delete attempt.
:::

### POST /api/contracts

Creates a new contract.

**Request Body:**

| Field | Type | Required | Description |
|-------|------|:---:|-------------|
| `customer_id` | integer | Yes | FK → `customers.id` |
| `service_id` | integer | Yes | FK → `services.id` (one service can serve many contracts) |
| `unit_id` | integer | No | FK → `units.id` — a contract can exist before a unit is assigned |
| `free_meeting_room_hours_per_month` | integer | No | Default: `0`, minimum `0` |
| `lockers_rented` | integer | No | Default: `0`, minimum `0` |
| `parking_spaces_rented` | integer | No | Default: `0`, minimum `0` |
| `other_benefits` | string | No | Free-text description |
| `status` | string | Yes | `active`, `renewed`, `expired`, `terminated` |
| `branch_location` | string | Yes | `ITP` or `CBP` (see enum below) |
| `monthly_rental_rate` | integer | Yes | Minimum `0` |
| `security_deposit` | integer | Yes | Minimum `0` |
| `date_start` | date | Yes | Lease start date |
| `date_end` | date | Yes | Must be on or after `date_start` |
| `notarization_date` | date | No | Date the contract was notarized (nullable) |
| `payment_mode` | string | Yes | See enum below |

**Business Rules (service/unit assignment):**

- The service must **not be soft-deleted** — otherwise `422` on `service_id`.
- If a `unit_id` is given, the unit must **not be soft-deleted** and **must belong to the specified service** — otherwise `422` on `unit_id`.
- The unit must currently be **`available`** (not `occupied`) — otherwise `422` on `unit_id`.
- `date_end` must be on or after `date_start` — otherwise `422` on `date_end`.

**Response (201):** Returns the created contract, including the derived `lease_term`.

### GET /api/contracts/{'{id}'}

Returns a single contract with the customer and their users loaded.

**Response (200):** Contract object.
**Error:** `404` if not found.

---

### PUT/PATCH /api/contracts/{'{id}'}

Updates a contract. All fields are optional (`sometimes`). The same service/unit assignment rules as `POST` are enforced; when `service_id` is not part of the request, the contract's existing service is used for the check.

**Request Body:** Same fields as `POST`, all optional.

:::caution
The `created_by` and `updated_by` fields are included in the update validation rules, meaning they can be set directly by the client. However, the `contracts` table does **not** have these columns in its schema — these values will be silently ignored or cause errors.
:::

**Response (200):** Updated contract object.

### POST /api/contracts/used-hours

Calculates the total meeting room hours consumed by a contract in a given month.

**Request Body:**

| Field | Type | Required | Description |
|-------|------|:---:|-------------|
| `contract_id` | integer | Yes | FK → `contracts.id` |
| `month` | string | Yes | Format: `Y-m` (e.g., `2026-07`) |

**Response (200):**

```json
{
  "contract_id": 1,
  "month": "2026-07",
  "total_hours_used": 8,
  "free_hours_available": 10,
  "remaining_hours": 2,
  "bookings": [...]
}
```

**Implementation Details:**
- Looks up the contract, then queries `Booking` records matching the contract's `customer_id` in the specified month
- Considers bookings with statuses: `COMPLETED`, `ONGOING`, `PENDING`
- Each booking's duration is rounded up to the nearest 5 minutes, then ceiling-divided to hours
- Returns the total hours used, free hours from the contract, and remaining hours

### Model: `Contract`

- **Traits:** `HasFactory` (no `SoftDeletes`)
- **Timestamps:** Enabled (`$timestamps = true`)
- **Fillable:** `customer_id`, `service_id`, `unit_id`, `free_meeting_room_hours_per_month`, `lockers_rented`, `parking_spaces_rented`, `other_benefits`, `status`, `branch_location`, `monthly_rental_rate`, `security_deposit`, `date_start`, `date_end`, `notarization_date`, `payment_mode`
- **Appended (derived):** `lease_term` — read-only, computed from `date_start`/`date_end`
- **Casts:** `status` → `ContractStatus::class`, `branch_location` → `BranchLocation::class`, `payment_mode` → `PaymentMode::class`, `date_start`/`date_end`/`notarization_date` → `date`
- **Relationships:**
  - `customer()` → `belongsTo(Customer::class)`
  - `service()` → `belongsTo(Service::class, 'service_id')`
  - `unit()` → `belongsTo(Unit::class, 'unit_id')`
- **Boot logic:**
  - `deleting` → Throws `\LogicException` (contracts **cannot** be deleted)

## Seeded Data

The production contract list (loaded via the gitignored `php artisan seed:contracts` command) seeds **6 contracts** — each linked to a real service (`Private Office`, `Dedicated Desk`, `Free Desk`, `Virtual Office PRO`) and, where the service type has a physical unit, a real unit (`G1-1`, `G2-1`, `A1`).

:::caution
Customer data in `seed:contracts` is currently **mocked** — no real customer records have been provided yet. The customer creation block (plus the placeholder lease values: `monthly_rental_rate`, `security_deposit`, dates, `payment_mode`, `notarization_date`) must be replaced with real data once it's ready, before running this command against production.
:::

:::note
Before running any of the real-data seeders (`php artisan seed:services`, `seed:units`, `seed:contracts`), read the **README** in the `private` folder under `ENSPACE_IT_FILES` (accessible with the intern email) — it documents the correct sequence for running the seeders for the `contracts`, `services`, and `units` tables.
:::

:::caution
**Keep the real-data seeder in sync with schema changes.** Whenever a migration changes the `contracts` table (new columns, renames, enum values, NOT NULL, etc.), update `seed:contracts` as well — otherwise it will fail or silently seed stale data.
:::

## Known Gaps (for the next set of interns)

The following are **not yet added/implemented** — confirmed against the current codebase:

- **`created_by` / `updated_by` are not real columns** — the update validation accepts them, but the `contracts` table has no such columns, so the values are silently ignored.
- **No termination/renewal tracking** — the lifecycle is only the `status` enum; there is no `terminated_at`, `renewal_date`, or notes column recording how/when a contract ended, and deletion is fully blocked by design.
- **`lease_term` is derived, not stored** — there is no raw integer term length or stored copy; it is always computed from `date_start`/`date_end`.
- **Unit status is not synchronized** — creating/updating a contract only *validates* that a unit is `available`; it never flips the unit's status to `occupied` (see the Known Gaps in [Units](./units)).
- **Seeding rework pending** — `ContractSeeder` currently creates 6 contracts bound to a placeholder "Default Seeded Service" (because it runs before `ServiceSeeder`); the planned 36 mock contracts (6 per real service) are not yet implemented.

## Security

| Aspect | Status | Details |
|--------|:---:|---------|
| **Authentication Middleware** | None | All routes are fully public |
| **Authorization Policies** | None | No `ContractPolicy` exists |
| **Role-Based Access** | None | Any visitor can view, create, and modify contracts |

:::danger
Contract details including benefits, rental amounts, lease dates, and status can be viewed and modified by anyone without authentication. This should be restricted in production.
:::
